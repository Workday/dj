# Create DJ Python Model

**Create** new **`.python.json`** + **`.python.py`** files for Python ETL models. These are **not** dbt SQL models — they are Python Models data pipelines that extract data from external sources (APIs, files, Jenkins jobs) or Trino tables and load results into Iceberg (or S3). Downstream dbt SQL models consume the output tables as sources.

**Author choice:** Pick one orchestration style and stay consistent unless the user explicitly asks for mixed logic:

| Style | Orchestrator | Typical use |
| ----- | ------------ | ----------- |
| **Pandas** | `extract → transform → load → post_load` | External ingest, nested JSON, ML, notebook-style logic |
| **SQL / Trino** | `extract → transform_and_load → cleanup` | Warehouse-native transforms, large joins, default scaffold |
| **Mixed** | Combine stages when needed | Valid when the user requests it — not required |

There is **no SQL-first gate** and **no enforced hybrid** (stage-then-SQL) unless the author chooses that path.

**`.python.py`** is the **source of truth for code** — it is scaffolded once when the model is created, then authored/edited directly (cells are delimited with jupytext `# %%` markers). **`.python.json`** holds model metadata plus a non-authoritative `cells` snapshot of the last notebook save; it is **not** used to regenerate `.python.py`. **Never** hand-edit **`_trino_io.py`**, **`_config.py`**, or **`_model_tasks.py`** — these are auto-generated by DJ Framework and reverted on edit.

## When this skill applies

Use this skill when the user mentions: python model, ETL, data ingestion, API fetch, CSV import, data pipeline, Python pipeline, data extraction, **python model topic**, **multi-model pipeline**, or **dependency chain**.

**Out of scope** — delegate to sibling skills:

- SQL `.model.json` files (staging/intermediate/mart) → `dj-create-new-model`
- `.source.json` files (registering a raw table as a source) → `dj-create-source`
- Lightdash YAML → `dj-edit-lightdash-yaml`
- Refactoring existing models → `dj-review-and-refactor-model`
- Migrating a legacy Jupyter notebook into a new python model → `dj-migrate-notebook-to-pymodel`
- Verifying a python model's output table against a legacy/reference table → `dj-verify-pymodel-parity`
- Documenting a topic's python models in a README → `dj-document-pymodels`

## Authoring mode

| Mode | How | When |
| ---- | --- | ---- |
| **Cells (UI)** | Create Python Model webview, then write code in the notebook / `.python.py` | Default for new models; the webview scaffolds a stub `.python.py` |
| **Developer** | Author `.python.py` directly; edit `.python.json` for metadata; add topic-level `_helpers.py` for shared code | Multi-model topics, shared S3/API utilities |

Shared topic helpers live at `dags/python_models/<group>/<topic>/_helpers.py` (one per topic). Import from sibling models as needed.

## Interactive gathering workflow

Ask the following in order. Batch related questions to minimize round-trips. **Skip the Q&A entirely** when the user supplies a complete spec (name, group, topic, DAG, transform style, output, dependencies).

### Step 1: Identity

| Field           | Rule                                                                      | Example                                   |
| --------------- | ------------------------------------------------------------------------- | ----------------------------------------- |
| **name**        | `^[a-z][a-z0-9_]*$`                                                       | `backstage_catalogs`                      |
| **group**       | One of: `ml`, `etl`, `analytics`, `others` (or project-configured groups) | `etl`                                     |
| **topic**       | `^[a-z][a-z0-9_]*$`                                                       | `api_data`                                |
| **description** | Free text (optional)                                                      | `Fetches catalog data from Backstage API` |

### Step 2: Single model vs multi-model topic

| Approach | How | Behavior |
| -------- | --- | -------- |
| **Single model (UI)** | Default **Create Python Model** form | One `.python.json` + scaffolded `.python.py` per submit |
| **Multi-model topic (agent / manual)** | Author `.python.json` files under the same `group` / `topic`, or use this skill to batch-write configs | Set per-model `name`, `description`, `depends_on`, and `upstream_sources`; DJ auto-infers trino `upstream_sources` from `depends_on` on JSON sync when omitted |

`source_etl` is excluded from the Create Python Model DAG picker (DJ manages it via the generated template). DAG wiring is applied silently on create.

### Step 3: DAG assignment

Ask which Airflow DAG(s) to attach the model to. Look at existing DAGs in the project (`dags/` directory). Utility/library modules may use `"dags": []`.

### Step 4: Transform strategy (author choice)

Ask which orchestration style the author wants. If undecided, offer brief heuristics only — do not block on SQL:

| Often pandas | Often SQL |
| ------------ | --------- |
| Nested JSON / API pagination | Filtering, joins, aggregations on warehouse data |
| ML preprocessing | Deduplication (`ROW_NUMBER`), window functions |
| Small external files | Large Trino-to-Trino transforms |

### Step 5: Data source type

| Source type          | Typical packages | Extract pattern                  |
| -------------------- | ---------------- | -------------------------------- |
| **REST API**         | `requests`       | HTTP GET/POST with pagination    |
| **Database / Trino** | `_trino_io`      | `read_partition_to_dataframe` or SQL via `execute_sql` |
| **CSV / file**       | `pandas`         | `pd.read_csv()` from local or S3 |
| **S3 objects**       | `boto3`          | List/download from S3 bucket     |
| **Custom**           | User-specified   | User provides extract logic      |

### Step 6: Output configuration

Present defaults and confirm overrides:

| Field                 | Default                      | Override?               |
| --------------------- | ---------------------------- | ----------------------- |
| `output.database`     | `glue_development`           | Yes                     |
| `output.schema`       | `opus_python_source`         | Yes                     |
| `output_type`         | `iceberg`                    | Yes (alternative: `s3`) |
| `output.write_mode`   | `overwrite_partitions`       | Yes                     |
| `output.partition_by` | `["portal_partition_daily"]` | Yes                     |
| `namespace`           | `python`                     | Yes                     |
| `compute`             | `kpo`                        | Yes (`airflow` for MWAA worker) |
| `kpo_size`            | `small`                      | Yes (when `compute` is `kpo`) |

**Confirm the write target before proceeding.** `overwrite_partitions` is destructive for affected partitions. State resolved `output.database` / `output.schema` / `write_mode` and get explicit confirmation when not using defaults. Never point a new model at production without confirmation.

### Step 7: Dependencies, lineage, and optional fields

| Field | Purpose |
| ----- | ------- |
| **depends_on** | Upstream **Python model names** — wires Airflow task order (model B waits for model A) |
| **upstream_sources** | Upstream **lineage** — written to Iceberg `python_model_upstream_sources` after each successful run |
| **dependencies** | Python pip packages (e.g. `requests>=2.28.0`) |
| **tags** | `python-model`, `api`, `csv`, `s3`, `trino`, `snapshot`, `iceberg` |
| **owner** | Team or individual |
| **enable_notebook** | Generate companion `.python.ipynb` (default: `true`) |

**`depends_on` vs `upstream_sources` — both matter:**

- **`depends_on`** — scheduling only. Tells Airflow which sibling Python models must finish first.
- **`upstream_sources`** — lineage only. Tells Model Lineage which Trino tables and external systems this model reads.

When a model reads another Python model's output table, set **both**: `depends_on` for task order and a `trino` entry in `upstream_sources` for the graph edge. DJ auto-infers trino `upstream_sources` from `depends_on` on JSON sync when the author omits them (appended, never overwriting declared entries).

**Governance metadata is optional — offer, never require.** Offer `owner_slack`, `pii`, `classification`, and `compliance` in `meta` (see `.agents/dj/reference/meta-and-governance.md`). If the user skips, write nothing.

### `upstream_sources` reference

Declare in `.python.json` only — DJ writes properties after each run; **do not** call `ALTER TABLE` for lineage in `.python.py`.

```json
"upstream_sources": [
  { "type": "trino", "value": "glue_development.opus_python_source.raw_events" },
  { "type": "external", "value": "api::backstage_catalog" },
  { "type": "external", "value": "s3::my-bucket/path/data.csv" },
  { "type": "external", "value": "jenkins::my-job-name" }
]
```

| `type` | `value` format | Notes |
| ------ | -------------- | ----- |
| **trino** | **`catalog.schema.table`** (canonical) | e.g. `glue_development.opus_python_source.model_a` |
| **trino** | `schema.table` (legacy) | Still parsed; prefer 3-part FQN for new models |
| **external** | Prefix convention | `s3::…`, `api::…`, `jenkins::…`, or other stable identifier |

## KPO and execution requirements

New models default to **`compute: "kpo"`** (Kubernetes pod). Set **`compute: "airflow"`** when the KPO image pipeline is not ready.

| Field | Purpose |
| ----- | ------- |
| `compute` | `kpo` (default) or `airflow` |
| `kpo_size` | Pod preset when `compute` is `kpo`: `small`, `medium`, `large`, `xlarge` |

**KPO script path:** The `mwaa-opus-kpo-runner` image syncs `s3://<bucket>/dags/python_models/` into the pod and runs `python <group>/<topic>/<name>.python.py`. Set Airflow Variable **`python_models_s3_bucket`**; optional **`python_model_s3_region`** (default `us-west-2`). Configure **`airflow_runner_cfg`** (image, tag, namespace, cluster).

**`PYMODEL_*` environment:** Airflow sets `PYMODEL_DS`, `PYMODEL_DS_NODASH`, and optionally `PYMODEL_DATES` (JSON array) before execution. `build_context_from_env()` in `_config.py` reads them and configures `logging.basicConfig` to stdout (required for KPO log visibility).

**`__main__` block (required):** Scaffolded `.python.py` must end with:

```python
if __name__ == "__main__":
    from python_models._config import build_context_from_env
    run_etl(build_context_from_env())
```

MWAA worker and KPO pod both execute the file as `__main__`. `run_etl` is scaffold convention, not a framework-enforced name.

**Airflow UI:** Each KPO model is **one task** named after the model `name` field.

## File path and naming

```
dags/python_models/<group>/<topic>/<name>.python.json
```

Model ID: `python__<group>__<topic>__<name>`

## ETL cell structure

The `cells` array uses notebook format: `cell_type` (`code` | `markdown`), `source` (array of strings ending with `\n`), optional `metadata`, `outputs`, `execution_count`.

### Pandas orchestrator

1. **Markdown header** — model name and DAG info
2. **Imports + logging** — `pandas`, domain packages, `from python_models._trino_io import read_partition_to_dataframe, overwrite_partition_from_dataframe`
3. **Output config** — `PythonModelConfig` from `python_models._config`
4. **Input variables** — model-specific constants
5. **`extract(context)`** — fetch external data or read Trino partitions into a DataFrame
6. **`transform(df, context)`** — pandas transforms; set `portal_partition_daily`
7. **`load(df, context)`** — `overwrite_partition_from_dataframe(table_fqn, …)`
8. **`post_load(context)`** — optional validation via `fetch_value`
9. **`run_etl(context)`** — orchestrate the stages
10. **Script entry** — `if __name__ == "__main__": run_etl(build_context_from_env())`
11. **Runner cell (optional, notebook only)** — a bare `run_etl(context)` for interactive notebook runs; keep it out of `.python.py` module scope so the file stays import-safe (the `__main__` block is the script entry)

### SQL / Trino orchestrator

1. **Markdown header**
2. **Imports** — `from python_models._trino_io import execute_sql, fetch_value, overwrite_partition`
3. **Output config** — `PythonModelConfig`, `get_catalog_name`
4. **Input variables**
5. **`extract(context)`** — optional staging (external → temp table via `create_iceberg_table` + batched inserts, or skip when source is already in Trino)
6. **`transform_and_load(context)`** — SQL transforms; `overwrite_partition(table_fqn, …)`
7. **`cleanup(context)`** — `execute_sql("DROP TABLE IF EXISTS …")` for staging tables
8. **`run_etl(context)`**
9. **Script entry** — `if __name__ == "__main__": run_etl(build_context_from_env())`
10. **Runner cell (optional, notebook only)** — bare `run_etl(context)` for interactive runs; not part of the `.python.py` module scope

### Table FQN (`table_fqn`)

All `_trino_io` helpers take a fully-qualified table string. Build it from Airflow variables and output config:

```python
table_fqn = f'{get_catalog_name()}.{OUTPUT_CONFIG.namespace}.{OUTPUT_CONFIG.table_name or OUTPUT_CONFIG.model_name}'
```

Use the same pattern for upstream tables declared in `upstream_sources`.

### `_trino_io.py` API reference

The extension auto-generates `dags/python_models/_trino_io.py`. **Do not edit it.**

**SQL path:**

| Function | Use when |
| -------- | -------- |
| `execute_sql(sql)` | DDL/DML with no return value (CREATE, DROP, INSERT, …) |
| `fetch_value(sql)` | Scalar reads (`SELECT COUNT(*)`, `SELECT MAX(…)`) — first column of first row |
| `overwrite_partition(table_fqn, partition_col, partition_value, *, insert_sql=…)` | Idempotent partition load — DELETE partition, then INSERT |
| `overwrite_partition(…, source_query=…, columns=[…])` | Same, but helper assembles `INSERT INTO … (cols) <query>` |
| `overwrite(table_fqn, filter, *, insert_sql=…)` | Conditional overwrite (`"true"` for full refresh) |
| `append(table_fqn, insert_sql)` | Append-only INSERT |
| `merge(table_fqn, merge_sql)` | Upsert via `MERGE INTO …` |
| `update(table_fqn, set_clause, where_clause)` | Standalone UPDATE |
| `create_iceberg_table(…)`, `create_schema(…)`, `set_extra_properties(…)` | DDL / metadata |

**Pandas path (python-path models only):**

| Function | Use when |
| -------- | -------- |
| `read_partition_to_dataframe(table_fqn, partition_col, partition_value, columns=None)` | Read one partition slice into a DataFrame |
| `overwrite_partition_from_dataframe(table_fqn, partition_col, partition_value, df, columns, batch_size=1000)` | Idempotent partition write from a DataFrame |

**Do not use:** `execute_trino`, inline `trino.dbapi.connect`, raw HTTP to Trino, or standalone `delete()` — partition overwrites go through `overwrite_partition` / `overwrite_partition_from_dataframe`.

**Example — SQL partition load:**

```python
from python_models._trino_io import overwrite_partition

def transform_and_load(context):
    ds = context["ds"]
    table_fqn = f"{get_catalog_name()}.{OUTPUT_CONFIG.namespace}.{OUTPUT_CONFIG.table_name}"
    insert_sql = f"""
        INSERT INTO {table_fqn}
        SELECT col_a, col_b, '{ds}' AS portal_partition_daily
        FROM {get_catalog_name()}.stg_tmp.my_staging_table
    """
    overwrite_partition(table_fqn, "portal_partition_daily", ds, insert_sql=insert_sql)
```

**Example — pandas partition load:**

```python
from python_models._trino_io import overwrite_partition_from_dataframe

def load(df, context):
    ds = context["ds"]
    table_fqn = f"{get_catalog_name()}.{OUTPUT_CONFIG.namespace}.{OUTPUT_CONFIG.table_name}"
    columns = ["col_a", "col_b", "portal_partition_daily"]
    overwrite_partition_from_dataframe(
        table_fqn, "portal_partition_daily", ds, df, columns
    )
```

**Example — scalar validation:**

```python
from python_models._trino_io import fetch_value

def post_load(context):
    ds = context["ds"]
    table_fqn = f"{get_catalog_name()}.{OUTPUT_CONFIG.namespace}.{OUTPUT_CONFIG.table_name}"
    count = fetch_value(f"""
        SELECT COUNT(*) FROM {table_fqn}
        WHERE portal_partition_daily = '{ds}'
    """)
    if not count:
        raise RuntimeError(f"No rows loaded for {ds}")
```

## After creating — developer checklist

1. **Code** — author the ETL directly in `.python.py` (scaffolded on create); confirm it has the `__main__` block and the chosen `_trino_io` imports.
2. **`depends_on`** — every upstream Python model this one waits on is listed.
3. **`upstream_sources`** — every Trino table and external system read by the model is declared (`catalog.schema.table` for trino).
4. **Output target** — `output.database` / `output.schema` / `write_mode` match the intended environment.
5. **Partition column** — `portal_partition_daily` is set in output (SQL `'{ds}' AS portal_partition_daily` or pandas assignment) when using partition writes.
6. **DAG wiring** — model appears in the selected DAG; KPO variables (`python_models_s3_bucket`, `airflow_runner_cfg`) are set.
7. **Register downstream source** — after first successful run, create `.source.json` via `dj-create-source` so dbt models can reference the table.
8. **Topic README (optional)** — run `dj-document-pymodels` for multi-model topics.

### Lineage expectations

After a successful Airflow or KPO run, DJ writes Iceberg table properties on the output table:

- `python_model_name`, `python_model_table`, `python_model_namespace`, `python_model_description`
- `python_model_upstream_sources` — JSON from `.python.json` `upstream_sources` (plus any auto-inferred trino entries)

Model Lineage reads these properties and walks upstream recursively:

- **Python model nodes** — output tables with `python_model_name`
- **Trino ref nodes** — `type: trino` upstreams (`catalog.schema.table`)
- **External nodes** — `type: external` upstreams (`s3::…`, `api::…`, etc.)

Chains like downstream dbt → model C → model B + model A render in one graph when each hop declares `upstream_sources`.

## Downstream dbt integration

Downstream dbt SQL models reference the output table using DJ source notation:

```
glue_development__opus_python_source.<table_name>
```

(Double underscore separates catalog from schema.)

Register the output table as a **`.source.json`** before a downstream model can read it — use **`dj-create-source`** or the `DJ: Create Source` webview, then sync.

## Optimization guidance

Surface relevant advice based on source type and volume; do not mandate SQL.

### Partitioning

- **Default:** `portal_partition_daily` for daily loads
- **Low volume:** `portal_partition_monthly` to reduce small files
- **High cardinality:** composite partitions for predicate pushdown

### Write modes

| Write mode | Use when |
| ---------- | -------- |
| `overwrite_partitions` | Idempotent daily loads |
| `append` | Append-only event streams |
| `overwrite` | Full table refresh |

### SQL transforms (when using SQL path)

- Enumerate columns explicitly — avoid `SELECT *`
- Filter on partition columns in WHERE clauses
- Use `CAST(… AS type)` for type safety
- Prefer `ROW_NUMBER()` for deduplication over pandas `drop_duplicates`

### Pandas transforms (when using pandas path)

- Batch large writes via `overwrite_partition_from_dataframe(…, batch_size=…)`
- Read upstream partitions with `read_partition_to_dataframe` instead of pulling full tables
- Chunk API pagination before building large DataFrames

## Conventions and gotchas

- **`.python.py` is the code source of truth** — edit it directly; `.python.json` holds metadata + a non-authoritative `cells` snapshot; `.python.ipynb` is an ephemeral view (in `.dj/.python_temp/`, auto-deleted on close)
- **`get_catalog_name()` / `get_namespace_name()`** — resolve catalog and schema from Airflow Variables; do not hardcode in production paths
- **Lineage in JSON only** — `upstream_sources` on `.python.json`, not manual property DDL in cells
- **`portal_partition_daily`** — required for partition-based writes
- **`depends_on`** — Airflow task ordering; **`upstream_sources`** — lineage graph edges; set both when reading sibling Python outputs
- **`_config.py`, `_trino_io.py`, `_model_tasks.py`, `etl_helper.py`** — auto-generated; do not hand-edit (edits are reverted)
- **Use `_trino_io` helpers** — no inline Trino connection code
- **Cell `source` format** — each element ends with `\n`
- **Notebook header** — the `# Python Model: …` cell is derived/notebook-only and never written back to `.python.py`
- **Name uniqueness** — model names unique across the project
